## 2. Method references

| Topic | Finding | Sources | Label |
|---|---|---|---|
| WAPE | `WAPE = Σ\|yₜ−ŷₜ\| / Σyₜ` (sum of errors over sum of actuals, **not** an average of per-period percentages — averaging SKU/day percentages is a named trap) | [Pigment](https://kb.pigment.com/docs/accuracy-measures.md), [Baeldung](https://www.baeldung.com/cs/mape-vs-wape-vs-wmape), [AWS Forecast docs](https://docs.aws.amazon.com/forecast/latest/dg/metrics.md) | S |
| Bias | `Bias = Σ(F−A) / ΣA`; positive = over-forecasting (sign convention varies by source, state yours) | [demandplanning.net slides](https://demandplanning.net/wp-content/uploads/2023/12/Forecast_Accuracy_Presentation_2023.pdf) | S |
| Why WAPE > RMSPE with many zero-sales days | MAPE/RMSPE divide *per row* by the actual, which is undefined/explodes at zero; WAPE aggregates numerator and denominator separately first, so zero-sales rows don't blow up the metric. No source directly benchmarks WAPE vs RMSPE on Rossmann-style zero-inflated data — this is the standard reasoning, not a specific study. | [Baeldung](https://www.baeldung.com/cs/mape-vs-wape-vs-wmape), [arXiv 2203.10716](https://arxiv.org/pdf/2203.10716) | S |
| Safety stock from forecast-error σ | `SS = z·σ_error·√(R+L)` using the std dev of **forecast error**, not raw demand — one source explicitly warns raw demand already contains seasonality/trend, so using it double-counts variability and inflates the buffer | [Lokad](https://www.lokad.com/calculate-safety-stocks-with-sales-forecasting/), [Cleverence](https://www.cleverence.com/articles/3pl-business/how-to-determine-and-use-safety-stock-levels-4382/) | S |
| Newsvendor / critical ratio | `CR = Cu/(Cu+Co)`; optimal order = the CR-quantile of the demand distribution; with an empirical distribution, optimal Q is the smallest value where the empirical CDF ≥ CR (discrete case has no exact solution) | [uni-koeln primer](https://scm.uni-koeln.de/sites/scm/Studium/Onlinekurs_-_Inventory_Management/Exercises/Primer_Ex2.pdf), MetricGate docs | S (standard textbook result) |
| Distribution families | **Negative binomial** (as a gamma-Poisson mixture) is the best-supported fit for per-store-day retail **unit counts** in the literature I found (several patents + an arXiv paper on full predictive distributions, which also flags slight zero-inflation and poor upper-quantile calibration for slow movers). For continuous turnover (Rossmann's Sales, in euros not units) I found **no direct gamma vs. lognormal vs. negative-binomial comparison** — treat your own choice as a modelling decision to justify, not a literature-confirmed pick. Laplace vs. normal for lead-time/forecast-error demand is directly tested in an old USAF logistics report (favors Laplace in some cases); more recent practitioner literature (IBF primer) argues normal is "rarely" the right assumption for demand and recommends probabilistic/empirical approaches instead. | [arXiv 2009.07052](https://arxiv.org/pdf/2009.07052), [IBF primer](https://ibf.org/knowledge/jbf-articles/a-primer-on-probabilistic-demand-planning-1270), USAF DTIC report | S for NB-on-counts; **U for gamma/lognormal/Laplace specifically fitting Rossmann's turnover column** |
| GoF practice (KS/AD caveat) | Confirmed and important: the classical KS p-value assumes known parameters. If you fit parameters from the same sample, the test statistic is biased toward "fits" and the classical p-value **overstates** the fit (one worked example: D dropped from 0.180 to 0.082 just from fitting params). Use a Lilliefors correction or a parametric bootstrap for the p-value instead of the textbook KS table. Pair with QQ-plots; chi-square needs binned counts and is sensitive to bin choice. | [KScorrect/Lilliefors docs](https://rdrr.io/cran/KScorrect/man/LcKS.html) | S |
| Promo uplift without leakage | Standard approach: fit a baseline model that **excludes** the promo window/promo features, forecast what sales "would have been", and treat actual−baseline as uplift. One practitioner source argues retrospective analysis doesn't count as leakage because you're explaining the past, not predicting the future — that reasoning is **shaky** if the baseline model is later reused for live replenishment forecasting (the leakage risk is real in that reuse case). Also account for cannibalization/forward-buying before calling it uplift; randomized holdouts are the clean answer but rarely available in retrospective Kaggle data. | [Artefact blog](https://www.artefact.com/blog/forecasting-something-that-never-happened-how-we-estimated-past-promotions-profitability-2) | S (practitioner blog, not peer-reviewed — treat as a pattern to adapt, not a standard) |

## 3. Power BI without Power BI Desktop

| Question | Finding | Label |
|---|---|---|
| Can a .pbix be generated/verified without Desktop? | **No tool found that does this.** PBIP/TMDL are text-based *storage* formats (a `.Report` folder + a `.SemanticModel` folder of TMDL files) that make Git diffs possible, but every source describes them as still opened and edited **in Power BI Desktop** — TMDL is a preview feature you enable inside Desktop (File → Options → Preview features), not a standalone editor or CLI. I found nothing suggesting a headless/CLI way to render or validate a .pbix/.pbip on this machine. | S |
| Does Desktop require a Microsoft account? | Third-party guides (not official MS docs) say core authoring works fully without signing in; sign-in is only needed to **publish** to the Power BI Service. No official Microsoft page confirming this was found. | S |
| Does Desktop require admin rights to install? | Microsoft's own docs (quoted by a third party) say: Microsoft Store install does **not** need admin rights; the direct **MSI** install **does** require admin. No per-user MSI option found. Since this machine has no admin rights mentioned, the Store route is the one to try — but it may be blocked by other policy; untested. | S |
| DAX pattern — WAPE/Bias | `WAPE = DIVIDE(SUMX(FactTable, ABS(Actual-Forecast)), SUM(FactTable[Actual]))`; Bias uses the same SUMX-then-DIVIDE structure with a signed difference. Key pitfall flagged by a Fabric community thread: a row-level measure doesn't auto-aggregate correctly across filter context — you need the outer `SUMX` over the fact table, not a plain `SUM` of a precomputed column. | S |
| DAX pattern — date table | `CALENDAR(mindate,maxdate)` wrapped in `ADDCOLUMNS` for Year/Month/Quarter; prefer explicit `DATE()` bounds via variables over `CALENDARAUTO()`, which scans every date column in the model (including unrelated ones) and can pull in irrelevant years. Table must have one row per day, zero gaps, spanning full years. | S ([SQLBI](https://www.sqlbi.com/articles/creating-a-simple-date-table-in-dax/)) |

**Bottom line for the build:** since Power BI Desktop isn't installed and may need a Store install (admin-free) to add, plan the P1 dashboard deliverable as **PBIP/TMDL source files that Taim imports/opens in Desktop himself**, with a Python/CSV-generated semantic model behind it, rather than assuming Claude can render or verify the .pbix end to end.

## 4. Risks a German hiring reviewer would spot (synthesis, not all individually sourced)

1. **Rossmann is one of the most-reused Kaggle sets** (general portfolio-mistake sources call generic/MOOC-style Kaggle projects an instant tell — "recruiters are now familiar enough with many MOOCs to instantly recognize" them). A reviewer who's seen 20 Rossmann XGBoost notebooks will skim past unless the DES/replenishment angle is visible in the first screen of the README. (S — general portfolio-mistake literature, not Rossmann-specific.)
2. **"Digital twin" as a label for a batch forecast + spreadsheet-style inventory formula** — German engineering/supply-chain interviewers (the dmTECH/MTU/Airbus postings in the GitHub research file) use "digital twin" to mean a live, stateful process model; calling a static forecasting pipeline a "digital twin" invites a pointed first question. Keep the DES (AnyLogic/SimPy) as the actual twin and the Python/SQL/Power BI work labelled as what it is: a forecasting and analytics pipeline. (U — reviewer reaction, not sourced, but consistent with the terminology precision German engineering interviews are known for.)
3. **Any committed raw CSV, cached database, or a `.pbix` with the Rossmann rows embedded** is both a licensing problem (already flagged hard in the playbook/GitHub research) and a visible giveaway that the Kaggle rules weren't read — a reviewer who knows Kaggle's redistribution clause will check this first.
4. **Euro-denominated claims treated as fact rather than assumption** — since this research could not confirm Sales is actually in EUR from an official source, any report sentence that states costs/savings "in €" without a footnote is overclaiming precision the data doesn't support (compounds the playbook's rule against fabricated precision).
5. **No German-language summary** despite the job postings surveyed (tesa, Lufthansa Technik) requiring German C1 — already flagged in the playbook, repeating here because it's the single easiest fix with highest reviewer visibility.
6. **Claiming the StateHoliday dtype trap, the store-622 test-set quirk, or the refurbishment gaps were "handled"** without being able to explain them in an interview — these are exactly the kind of cleaning-code questions ("walk me through how you handled StateHoliday") a technical interviewer uses to check if the candidate wrote the pipeline themselves vs. copied a notebook.
